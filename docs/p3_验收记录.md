## 二、招牌链路：查→订 A2A 串联（日志证据）

预订 Agent 落单前，先以 A2A 协议调查询 Agent 复查目标时段：

```
meeting_book.serial_check | room='A-802' date='2026-10-06' slot='15:00-16:00' available=True  candidates=9   → 复查通过 → 落单成功
meeting_book.serial_check | room='A-501' date='2026-10-06' slot='15:00-16:00' available=False candidates=8   → 不可用 → 返回备选追问
meeting_book.serial_check | room='A-802' date='2026-10-06' slot='16:00-17:00' available=True  candidates=10  → 改期目标可用 → 改期落单
```

设计要点：
- 查询结果只作**参考**，不参与最终一致性——真正的兜底在 OA 侧事务（P1 已验证并发只成功一人）；
- 复查在**落单前**做，竞争窗口内的冲突由 MCP 返回 `conflict`，Agent 再复查备选并追问（验收用例 4 覆盖不可用路径）。

## 四、问题与修复（P3 踩坑）

**现象**：首跑 4 项失败，`input-required` 的 `message` 字段全为空（追问文案丢失）。

**分析**：追问文案最初写在 `task.message` 上；python-a2a 序列化时，客户端读的是 **`status.message`**，`task.message` 不会被传出。

**修复**：`contract.py` 的 `input_required()` / `failed()` 改为把文案写进
`TaskStatus(state=..., message={"role": "agent", "content": {"text": ...}})`（与 SmartVoyage 的写法一致）。

**附**：同批修正查询 Agent 回答格式——列出房间时带上 **room_id**（如 `A-801 A栋801 会议室（12人）`），因为下一步预订需要它。
