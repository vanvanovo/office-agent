## 二、验收证据

### 2.1 注入 payload 回归（10 类，全部安全）

```
' OR '1'='1 ｜ " OR "1"="1 ｜ '; DROP TABLE equipment; -- ｜ %' UNION SELECT ... ｜ admin'--
1; DELETE FROM equipment ｜ % ｜ _ ｜ 投影仪' OR 1=1 -- ｜ 2000 字符长输入
→ 全部被当作普通字面量处理（参数绑定），无一泄漏/报错/副作用
```

### 2.2 完整性 / 工具面 / 写入面 / 越权面

```
[2] 注入后：equipment 仍 32 条、repair_tickets 表未删除
[3] 工具面：OA MCP（8 个工具）、器材 MCP（7 个工具）均无 `sql` 参数
[4] 写入面：book_room 注入式 room_id 不产生任何脏数据
[5] 越权面：取消他人预订被拒 / 不存在工单催单被拒
```

### 2.3 反例对照演示

```
员工输入： %' OR '1'='1' --
[旧模式] 拼接 SQL：SELECT ... LIKE '%%' OR '1'='1' --%'  → 返回全表 3 行（被注入）
[新模式] 参数绑定：SELECT ... LIKE ?  [payload 当普通字符串] → 0 行命中（安全）
[正常输入] 关键词=投影仪：两种模式都 1 行（功能等价）
→ [PASS] 同样输入：旧模式被注入、新模式安全
```

## 三、过程记录（如实）

- 首跑安全测试时发现**测试自身有假阳性**：`tools/list` 响应解析用了 `tools/call` 的结构，导致"0 个工具"也判定通过。已修复并加断言（工具数达标且无 sql 参数），复跑通过。
- 脚本 emoji 在 GBK 控制台崩溃的问题同前，已统一为 ASCII 标记 + `errors="replace"` 兜底。

## 四、设计口径（SQL 白名单）

器材查询参考的开源写法是"让大模型生成 SQL 字符串"（工具签名 `query_tickets(sql)`）。安全用例复现了注入面——拼接 payload 能让 WHERE 恒真、拖出全表——随后把工具层彻底改为**白名单模板 + 参数绑定**：模型只负责选工具、填参数；并补了 10 类 payload 的回归用例。现在两个 MCP 服务的工具签名里没有任何 `sql` 参数。`scripts/security/legacy_free_sql_demo.py` 保留复现证据。
